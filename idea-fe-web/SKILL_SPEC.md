# 技能开发规范

## 1. 技能定义与核心原则

### 1.1 什么是 Skill？

Skill 是一份清晰、严谨、可执行的指令文档，用于明确告诉模型：
- **When（何时）**：在什么条件下触发该技能
- **How（如何）**：按照哪些步骤执行
- **What（结果）**：产出什么结果

### 1.2 核心设计原则

| 原则 | 描述 |
|-----|------|
| 边界明确 | 明确正向触发条件和负向排除条件 |
| 输入输出结构化 | 定义双方都能理解的 Input/Output 格式 |
| 步骤可执行 | 使用指令式、具体动作描述步骤 |
| 失败策略完备 | 定义各种失败场景的处理方式 |
| 职责单一 | 每个 Skill 只做一件事，对应一个核心动作 |

### 1.3 常见认知误区

- ❌ Skill ≠ Prompt：Skill 是可长期复用的能力模块，不是一次性对话提示
- ❌ Skill ≠ 给人看的文档：目标是约束模型行为，不是解释原理
- ❌ 越复杂越强大：复杂度与能力强度无关，职责单一更易命中

## 2. SKILL.md 文件格式规范

### 2.1 Frontmatter 规范

```yaml
---
name: skill-name
description: 描述技能功能和使用场景，包含触发时机关键词
metadata:
  version: "1.0"
  author: "team-name"
license: MIT
compatibility: Requires Node.js 18+
---
```

**字段约束：**

| 字段 | 必填 | 约束 |
|-----|-----|------|
| name | 是 | 1-64 字符，仅小写字母、数字、连字符，不以连字符开头/结尾 |
| description | 是 | 1-1024 字符，描述功能和触发时机，使用第三人称 |
| metadata | 否 | 键值对，可包含 version、author 等信息 |
| license | 否 | 许可证名称或文件引用 |
| compatibility | 否 | 环境要求，最大 500 字符 |

### 2.2 Body 内容结构

```markdown
# 技能名称

## 描述
简短描述技能的作用和价值

## 触发条件
### 适用场景
- 场景1
- 场景2

### 不适用场景
- 场景1
- 场景2

## 输入输出定义
### Input
- 参数名: 类型 - 描述（是否必填）

### Output
- 参数名: 类型 - 描述（是否可选）

## 执行步骤
1. 步骤1
2. 步骤2
3. 步骤3

## 失败策略
- 失败场景1: 处理方式
- 失败场景2: 处理方式

## 示例（可选）
### 输入示例
xxx

### 输出示例
xxx

## 注意事项
- 注意事项1
- 注意事项2
```

## 3. 目录结构规范

```
skill-name/
├── SKILL.md          # 必须：核心指令文档
├── scripts/          # 可选：可执行脚本
│   └── run.sh
├── references/       # 可选：参考文档
│   └── API.md
├── assets/           # 可选：模板、资源文件
│   └── template.json
└── examples/         # 可选：输入输出示例
    ├── input.md
    └── output.md
```

**目录职责：**

| 目录 | 职责 |
|-----|------|
| scripts/ | 存放可执行代码，需自包含并处理异常 |
| references/ | 存放详细技术文档，按需加载 |
| assets/ | 存放模板、配置文件、静态资源 |
| examples/ | 存放输入输出示例 |

## 4. 编写最佳实践

### 4.1 渐进式披露原则

1. **Metadata（~100 tokens）**：name 和 description 在启动时加载
2. **Instructions（< 5000 tokens）**：SKILL.md 主体在激活时加载
3. **Resources（按需）**：引用文件仅在需要时加载

**实践要点：**
- SKILL.md 主体控制在 500 行以内
- 避免深度嵌套引用（保持一层）
- 长文件添加目录（Table of Contents）

### 4.2 触发条件编写技巧

**适用场景示例：**
```markdown
## 适用场景
- 用户意图是触发 CI/CD 流水线执行单元测试
- PR 状态为"待合并"，需要执行自动检查或 lint 校验
```

**不适用场景示例：**
```markdown
## 不适用场景
- 用户只是查看测试报告或 CI/CD 状态
- PR 内容没有代码改动，仅修改文档或注释
```

### 4.3 输入输出定义规范

```markdown
## 输入输出定义
### Input
- prId: string - PR 编号（必填）
- branch: string - 分支名称（必填）
- runTests: boolean - 是否执行单元测试（可选，默认 true）

### Output
- success: boolean - 是否成功执行
- testReport?: object[] - 测试报告（可选）
- errorMessage?: string - 错误信息（失败时返回）
```

### 4.4 步骤编写规范

使用指令式语言，避免描述性语言：

✅ 好的示例：
```markdown
## 执行步骤
1. Validate PR: 检查 prId 和 branch 是否有效
2. Checkout branch: 切换到指定分支
3. Run tests: 根据 runTests 参数执行单元测试
4. Collect results: 收集测试结果
5. Update PR status: 将测试状态回写到 PR
6. Notify user: 若测试失败，返回错误信息
```

❌ 坏的示例：
```markdown
## 执行步骤
检查 PR，运行测试，然后更新状态
```

### 4.5 失败策略编写规范

```markdown
## 失败策略
- Validation fails: 返回 400 Bad Request，并附上具体错误信息
- Test execution fails: 自动重试一次，仍失败则返回"单元测试未通过，请检查日志"
- CI/CD 服务不可用: 重试最多 3 次，仍失败则记录日志并通知管理员
```

## 5. 技能构建与迭代流程

### 5.1 第一步：建立基线，识别问题

不使用 Skill，直接让模型执行任务，记录：
- 不稳定或不可复现的情况
- 引发歧义、误解或走偏的输入
- 模型在错误时机"主动帮忙"的情况

### 5.2 第二步：定义评测用例

针对识别的问题，设计 3-5 个具体用例：
- 明确通过/失败判定标准
- 优先覆盖最易误用的场景

### 5.3 第三步：编写最小化 Skill

只编写刚好通过评测的最小规则：
- 明确失败条件
- 定义最短成功路径
- 保持职责单一

### 5.4 第四步：补充边界条件与示例

- 补充边界场景及行为约束
- 明确 Input/Output 结构化定义
- 添加关键输入输出示例

### 5.5 第五步：评测回归与迭代

- 新增评测用例推动增量修改
- 任意修改必须通过回归验证
- 未通过时优先简化，而非叠加规则

### 5.6 第六步：真实使用校准

观察真实场景中的问题：
- 非预期场景误触发
- 遗漏关键参考文件
- 反复读取某段内容形成隐性依赖

## 6. 反模式检查清单

| 检查项 | 反模式描述 |
|-------|----------|
| 命名不规范 | 使用大写字母、连续连字符、语义模糊的名称 |
| 描述不完整 | 缺乏触发时机关键词，使用第一人称 |
| 边界模糊 | 只定义适用场景，未定义不适用场景 |
| 功能捆绑 | 一个 Skill 包含多个核心功能 |
| 步骤模糊 | 使用描述性语言而非指令式语言 |
| 失败策略缺失 | 未定义失败场景的处理方式 |
| 文档过长 | SKILL.md 超过 500 行，未拆分到 references |
| 嵌套过深 | 引用文件存在链式依赖（A → B → C） |
| 魔法数字 | 代码中常量缺乏解释和来源说明 |
| 异常未处理 | 脚本直接抛出异常，未转化为可理解的输出 |

## 7. 命名规范

### 7.1 Skill 名称规范

| 规则 | 示例 |
|-----|------|
| 使用小写字母、数字、连字符 | `running-tests` |
| 推荐使用动名词形式 | `deploy-microservice` |
| 语义清晰，唯一标识 | `database-migration` |
| 长度不超过 64 字符 | ✅ |

### 7.2 文件命名规范

| 文件 | 命名 |
|-----|------|
| 核心文档 | `SKILL.md`（大写） |
| 参考文档 | `references/REFERENCE.md` |
| API 文档 | `references/API.md` |
| 脚本文件 | `scripts/run-{action}.sh` |

## 8. 验证与测试

### 8.1 格式验证

使用 `skills-ref` 工具验证：
```bash
skills-ref validate ./my-skill
```

### 8.2 功能测试

| 测试类型 | 内容 |
|---------|------|
| 触发测试 | 验证正确场景触发，错误场景不触发 |
| 执行测试 | 验证步骤正确执行，输出符合预期 |
| 失败测试 | 验证失败策略正确处理异常 |
| 回归测试 | 确保修改不破坏现有功能 |
